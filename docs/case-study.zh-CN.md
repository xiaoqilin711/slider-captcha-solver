# 案例复盘：自动化处理某商业滑块验证码

> 目标身份已完全脱敏。本文是 `slider-captcha-solver` 仓库背后的复盘——时间线、死路、以及两个不明显的密钥（`+10px` 偏移和"快冲慢调"轨迹）是如何被找到并标定的。

## 目标与背景

某技术论坛在**较老的文章**（约 2024 及更早）上会触发某商业滑块验证码，新文章则不会。任务：自动化处理滑块，让采集流程无人介入地拿到完整正文。

厂商的 JS 包版本号为 **2.28.5**——较新的一代，公开资料多为更老版本。

## 一句话链路

```
老文章触发滑块
  -> 本地 Pillow 缺口检测           （死路：1-32px 不稳定）
  -> 第三方 OCR                     （可行：同图 4 次识别一致）
  -> 抓包 + DOM 侦察                （getconf/get/check、滑块几何）
  -> 拖距 = OCR x1                  （死路：check false）
  -> 手动拖一次标定偏移             （距离 = x1 + 10）
  -> 对称"拟人"轨迹                 （死路：check 根本不发）
  -> 复刻真实采集轨迹               （可行）
  -> check true + validate          -> 服务端 verify -> 正文 108 -> 29236
```

## 1. 第一个异常：验证码"自己消失了"

早期有一次访问直接出正文、没有滑块。诱人的假设是"风控自动解除了"。用两个 context 做实验——同 IP/浏览器/UA，一个有 cookie、一个干净——一锤定音：

| Context | Cookie | 结果 |
|---|---|---|
| 已有会话 | 有 | 正文 29298，无滑块 |
| 全新无痕 | 无 | 正文 111，**有滑块** |

结论：**session 级放行，不是 IP 级**。同 IP 换个干净 context 立刻重新触发。

> 教训：一次只变一个变量，别把"两个现象同时发生"当成因果。

## 2. 缺口定位：本地算法 vs OCR

本地检测器（纯 Pillow，无 numpy/OpenCV）做法：灰度 → 边缘滤波 → 提取拼图块 alpha 边界像素 → 在背景边缘图上滑窗取最大响应。思路没问题，精度不行——同一张图结果在 1-32px 之间漂。OCR 读到 `x1=144` 时，它曾返回 `164`，差 20px。对差几个像素就判失败的滑块，这精度不可用。

第三方 OCR（`question=框出正确位置`）返回嵌套框，解析结构有讲究——box 是双层嵌套：

```python
x1 = json.loads(r["msg"])[0]["box"][0][0]   # box 是 [[x1,y1,x2,y2]]
```

同图连续识别 4 次，`x1=144` 纹丝不动（仅 `y2` 抖动 ±1），每次约 0.9s。**OCR 才是正确的缺口定位器；本地算法是死路，该放弃，别再回头。**

## 3. 协议与 DOM 侦察

厂商初始化是三次 JSONP 调用：

- **`getconf`** — 配置：JS 版本、图片服务器、zone、API 服务器。
- **`get`** — 返回 `bg`（带缺口的背景图）、`front`（拼图块）、`token`、`type=2`（滑块）、`waitTime`。
- **`check`** — 接收拖动，返回 `result:true` + `validate`（base64）。

DOM 几何（`getBoundingClientRect`）：

| 元素 | 尺寸 |
|---|---|
| 滑块按钮 | 40×38 |
| 轨道 | 320×40 |
| 背景图 | 320×160 |
| 拼图块 | 约 61×160 |

两个结论：背景图按**原始 320×160** 渲染，所以 OCR 像素坐标与页面像素 1:1（无需缩放）；40px 按钮 vs 61px 拼图块，正是下面推导 `+10` 要用到的。

事件层：前端监听的是 **document 级 `mousedown`/`mousemove`/`mouseup`**，不是 pointer 事件。Playwright 的 `page.mouse` 映射到 CDP `Input.dispatchMouseEvent`，正好落在这层——所以合成 pointer 事件没用，`page.mouse` 才行。

## 4. 一次手动拖，拿到 ground truth

真人拖了一次，同时记录轨迹。这一个样本同时暴露两个真相：

```
OCR box=[119, 28, 174, 86]  左边缘 x1=119
[check] true
用户实际拖距 = 129px，耗时 = 1042ms
x1 - 拖距 = -10px
64 个 move 点，dt min=5 max=178 avg=13.0ms
```

1. **距离 = OCR x1 + 10**——OCR 给的是缺口框的*左边缘*，正确的拖距要多 10px。
2. 真实形态：64 个 move 点、129px、约 1s，8-9ms 采样夹杂停顿。

第一次采集轨迹丢了，因为成功后页面导航清掉了 `window.__user_trace`。修复——按间隔把点捞到 Python 侧——成了 `trace_recorder.py`：

```python
while not done:
    time.sleep(0.3)
    pts = page.evaluate("() => { const a = window.__user_trace || []; window.__user_trace = []; return a; }")
    trace.extend(pts)
```

## 5. 距离之谜：为什么 +10

第二个目标（不同文章、不同缺口）确认偏移是固定的、不是一次性：

```
OCR box=[106, 95, 162, 155]  x1=106 -> 拖 116
[check] true  -> 正文 29236，URL -> ...-1.htm
```

几何解释：OCR 用约 55px 宽的框框住缺口（左边缘即 x1），拼图块 61px、按钮 40px。框宽一半减去按钮一半，再加 OCR 框定位偏差，落在 10px 附近。

**关键**：偏移是"每目标实测"的经验常数，*不是*协议里读出来的值。换目标或换 OCR 模型都要重新标定。

## 6. 轨迹之谜：为什么 check 发不出去

距离对了，形态又成了拦路虎：

| 轨迹 | 是否发 check | 结果 |
|---|---|---|
| 对称加减速 + 3px 回弹 + y±1.5 | **否** | None |
| 均匀减速、无回弹 | 是 | false（当时距离错） |
| 复刻真实轨迹 | 是 | **true** |

"拟人"轨迹——加减速、过冲回弹、y 抖动——在 check 请求发出前就被前端丢弃了。回弹和大 y 抖动让前端在 mouseup 时直接丢掉这次拖动。

第二个坑：`check result=None` **不代表**没发出。成功时页面立即跳转，Playwright 的响应监听随 context 销毁。判断成败要看**最终状态**（正文长度、URL），不是看监听返回值。

## 7. 真实轨迹："快冲慢调"

把采集到的 64 点按三分段分析：

| 段 | 位移 | 耗时 | 速度 |
|---|---|---|---|
| 前 1/3（21 点） | 84px | 166ms | **506 px/s** |
| 中 1/3（21 点） | 27px | 167ms | 162 px/s |
| 后 1/3（22 点） | 14px | 469ms | **30 px/s** |

人先把滑块一把拽到 65% 左右，再在缺口附近 0-1px 地精调。四个停顿点（`dt > 30ms`）：索引 0（46ms）、56（74ms）、61（50ms）、63（178ms）——最后一个是"到位后顿一下再松手"。y 噪声几乎为零：64 点里只有 4 个动了 1px，其余全 0。

复刻方式即 `scale_to_distance`——把位移序列归一化到单位距离、缩放到目标、保留原始时间间隔。完整序列见 `examples/profile_slider_vendor.py`。

## 8. 隐蔽的性能坑：图片怎么下载

- 页面内（浏览器）下载背景图：**10-30s**。
- `ctx.request.get()`（直连 API 取回）：**约 0.2s**。

差别不在字节，而在 `get` 响应里的 `token` 有生命周期。下载慢 → get→check 间隔拉长 → token 过期，这正是"有时莫名其妙失败"的根因。**背景图用 `ctx.request.get()` 下载，OCR 压在 ~1s 内。**

## 9. 最后一步：check → verify

两段式确认：

- `check` — 前端提交拖动，拿到 `result:true` + `validate`。
- `verify` — 站点*服务端*拿 `validate` 调厂商；这次调用浏览器不可见，只能间接确认。

verify 放行的证据：正文长度 108 → 29236、URL 跳到文章页。额外红利：放行是 **session 级、约 1 小时免验证**——趁热在同一 session 里继续采，而不是每篇重新拖。

## 成果

1. `拖动距离 = OCR x1 + 10`（每目标标定）。
2. 参考轨迹：64 点，按 `sum(dx)=129` 归一化，形态"快冲慢调"（完整序列在 profile）。
3. 可复用库：`track`、`ocr`、`drag`、`capture`、`trace_recorder`、`probe`、`dom`——全部与站点无关，纯逻辑部分有测试。
4. 背景图用 `ctx.request.get()` 下载，别用页面。

## 诚实边界

- **前端事件模拟，不是算法级破解**：厂商前端自己算 `validate`，我们从未伪造。
- 偏移与轨迹是**针对某一目标某一时刻标定的快照**，需按目标重新标定。
- 缺口定位依赖**第三方 OCR**，无自研检测器。
- `verify` 是**间接确认**的（页面跳转），不是抓到的。
- 只有 `track` 和 `capture` 有单元测试；浏览器路径需要真实授权目标。

## 复盘

四个真正的转折点，其余都是围绕它们的试错：

1. **锁定已被证明可用的工具**（OCR），别退回死路（本地算法）。
2. **一次手动拖作为 ground truth**，胜过十几轮盲调——它同时暴露了偏移和轨迹形态。
3. **看最终状态，不看中间监听的返回值**——否则 `check None` 和 `-1.htm` 都会伪装成失败。
4. **先排除隐藏变量**（图片下载时间/token 过期），再信任这条闭环。
